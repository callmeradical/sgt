## 2026-09-03 - Added index to phases on run_id
**Learning:** Found a missing index on a frequently queried foreign key column (`phases.run_id`). Adding a simple index drops query time significantly (from ~140ms to ~12ms for a loop of 100 iterations on a table with 10k rows).
**Action:** Always check foreign key queries against tables to ensure they have indexes, especially on ones likely to grow linearly with the number of test runs or phases (like `phases` linked to `runs`).
## 2026-09-16 - Add missing indexes for critical foreign keys
**Learning:** Found multiple foreign key columns without indices (`envelopes.run_id`, `deliveries.envelope_id`, `bullets.intent_id`, `artifacts.run_id`). Without these, any SELECT or DELETE operating via a foreign key (like cascading deletes during retention rotation, or listing bullets for an intent) required a full table scan.
**Action:** When adding tables with foreign keys that scale with the number of test runs or intent workloads, always ensure indices are created in `migrateAddIndexes()` to maintain performance and avoid N+1/table scan issues.
## 2024-05-20 - SQLite Composite Indexes for Filtering and Sorting
**Learning:** SQLite requires specific composite indexes to avoid temp B-trees and full table scans when a query filters by one column (e.g., `WHERE project = ?`) and sorts by another (e.g., `ORDER BY created_at DESC`). Simple single-column indexes on the WHERE clause are not enough to prevent the temporary B-tree sorting penalty on large core tables like `runs` and `intents`.
**Action:** Always create composite indexes mapping exactly to the `(filter_column, sort_column [direction])` for frequently executed, paginated, or ordered reads in SQLite stores.
## 2026-10-06 - Chunking SQLite IN clauses
**Learning:** SQLite has a variable limit (`SQLITE_MAX_VARIABLE_NUMBER`) which restricts the number of parameters you can pass in an `IN (...)` clause. When dealing with arrays of IDs that can grow large (like reconciling an unbounded number of orphaned runs after a crash), passing them all into a single query causes the query to fail.
**Action:** When using `IN (?)` with dynamically sized slices (especially things scaling with runs, phases, etc.), chunk the slice into smaller batches (e.g., chunks of 500) and execute the query iteratively.
## 2026-10-14 - Composite FK indexes must match a real query's ORDER BY
**Learning:** Single-column FK indexes (`phases.run_id`, `envelopes.run_id`, `bullets.intent_id`, `artifacts.run_id`) still forced a TEMP B-TREE sort on every list query, `ListRecentRuns` sorted the whole `runs` table, and the `deliveries` idempotency-key reads scanned the table because the only index on that column is partial (terminal rows). A composite only helps when a query's WHERE + ORDER BY actually match it: `deliveries(envelope_id, created_at, id)` does not, since `ListDeliveriesForRun` orders rows from several envelopes.
**Action:** Pair each composite with the query it serves and pin it with an `EXPLAIN QUERY PLAN` test (`TestHotListQueriesReadInIndexOrder`); drop a superseded prefix index only after its replacement exists, and check the DROP's error.
## 2026-10-19 - Missing Query Coverage in EXPLAIN QUERY PLAN Tests
**Learning:** Found multiple critical list queries (`ListRunsForProject`, `ListIntentsForProject`, `ListIntentsByStatus`) that did not have their indices pinned via `EXPLAIN QUERY PLAN` test cases in `TestHotListQueriesReadInIndexOrder`. Their inline strings made production SQL easy to duplicate and drift in tests. Although the codebase had previously created indexing strategies (`runsProjectIndex`, `intentsProjectIndex`, `intentsStatusIndex`) in the schema, it never tested them.
**Action:** When adding new list/sort queries in the SQLite store, ALWAYS declare their raw SQL string as a `const` and append the case to `TestHotListQueriesReadInIndexOrder`. This ensures SQLite is definitely using the composite index rather than performing full scans or falling back to a temp B-TREE sort on regressions.
## 2026-10-20 - SQLite Composite Indexes with Inequality and IN clauses
**Learning:** `ReconcileOrphanedRuns` benefits from `(status, created_at)`. `RunsEligibleForCleanup` needs `(updated_at, status)` for index-order reads, but SQLite otherwise prefers the status-leading reconciliation index and retains a TEMP B-TREE; pinning the query with `INDEXED BY` makes the intended plan deterministic. SQLite can scan `(project, created_at DESC)` backward for `RotateProject`, so a second ascending index is redundant.
**Action:** Pin every maintenance index to its production SQL with `EXPLAIN QUERY PLAN`, reject TEMP B-TREE sorts, and match the exact index name so a similarly prefixed index cannot satisfy the assertion accidentally.
## 2024-05-20 - SQLite TEMP B-TREE penalty with IN clauses
**Learning:** Found an unnecessary `ORDER BY` clause inside an `IN (...)` bulk fetch that caused SQLite to use an expensive `TEMP B-TREE` sort during application start. Even with an index covering the foreign key (e.g. `idx_phases_run_id_created_at`), querying for rows matching an array of parent IDs (e.g. `WHERE run_id IN (...) ORDER BY created_at ASC`) bypasses the strict ordered index properties because `IN` creates an unordered set to evaluate. If the order of the results doesn't matter (e.g. they are just being placed into a map by run ID), removing the `ORDER BY` clause speeds up execution significantly.
**Action:** When querying rows using an `IN (...)` clause to bulk fetch relationships (e.g. avoiding N+1 queries), remove any `ORDER BY` clause if the consumer does not require strict sorting to avoid unnecessary in-memory TEMP B-TREE sorts.
